## 1. 方案概述

本方案為一套以 LINE 官方帳號為介面的 AI 智慧接待系統，供商業服務業店家導入，用於自動處理顧客的常見詢問、價格說明、營業時間、地點指引、預約登記與客訴初步應對，並支援**繁體中文語音訊息**輸入。

系統設計原則為「規則優先、AI 補充」：

1. **規則層**：常見問題以關鍵字規則比對，即時回覆、措辭完全可控、無推論成本、無幻覺風險。
2. **AI 層**：規則未命中時，交由大型語言模型依「公司事實資料」生成回覆，並以提示詞約束禁止編造。
3. **轉人工**：AI 無法回答時，明確告知將由專人確認，並即時通知店家負責人。

此架構使店家能在**不需要具備技術背景**的情況下導入，且所有對外措辭（尤其價格、優惠、合約條件）皆由店家事先設定，不任由模型自由生成。

---

## 2. 適用業別與導入對象

適用於具備下列特徵之商業服務業店家：

- 有大量重複性顧客詢問（營業時間、價格、位置、服務項目、預約）
- 人力精簡，無專職客服人員
- 顧客溝通主要透過 LINE
- 需要 24 小時接住詢問，但無法 24 小時派員

**已驗證業別**：教育服務業（補習班）——本方案已於關係店家實際每日運作。
**規劃適用業別**：診所／牙醫／醫美、餐飲、零售、美容美髮、會計師事務所、健身與其他預約型服務業。

## 3. 系統架構

```
顧客 (LINE App)
    │  文字訊息 / 語音訊息
    ▼
LINE Messaging API  ── webhook (HTTPS)
    ▼
Cloudflare Tunnel（TLS 終止、固定網域、不開放任何 inbound 埠）
    ▼
應用主機（台灣境內）
    │
    ├─ 簽章驗證 (HMAC-SHA256)
    ├─ 文字 → 規則比對 → LLM 補充 → 回覆
    └─ 語音 → 下載 → 音訊轉檔 → 語音辨識 → 同上流程
    │
    ├─▶ LINE Reply API（回覆顧客）
    ├─▶ 對話紀錄（JSONL，90 天自動刪除）
    └─▶ 負責人即時通知（Telegram；僅限需要人工處理之訊息）
```

**架構特性**：

- **不對外開放任何 inbound 通訊埠**。對外連線僅透過 Cloudflare Tunnel 的 outbound 連線建立，主機無公開 IP、無 port forwarding、無防火牆例外。
- **可攜性**：系統以固定網域對外，主機可整批遷移而不需變更 LINE 設定，亦不影響店家已累積的顧客好友與對話。
- **租戶隔離**：同一主機可執行多個獨立店家實例，各自使用獨立連接埠、獨立憑證檔、獨立資料檔。

## 4. 功能規格

### 4.1 規則意圖（8 類，即時回覆）

| 意圖 | 觸發範例 | 行為 |
|---|---|---|
| 問候 greet | 你好、hi、在嗎 | 歡迎語 + 服務引導 |
| 價格 price | 多少錢、收費、方案 | 回覆店家設定之方案與價格 |
| 地點 location | 在哪、地址、怎麼去 | 回覆地址與交通說明 |
| 時間 hours | 幾點、營業時間 | 回覆服務時間與非營業時間處理方式 |
| 預約 booking | 預約、報名、想諮詢 | 引導提供日期時段，並通知負責人 |
| 情緒 emotion | 很差、太貴、失望、抱怨 | 致歉與安撫，避免制式罐頭回覆 |
| 服務項目 services | 你們做什麼、服務內容 | 列出服務範疇並詢問業別 |
| 品牌 about | 你們是誰、公司介紹 | 品牌與定位說明 |

**特性**：規則回覆為字串比對，延遲近乎 0（實測 < 0.01 秒），且措辭 100% 由店家控制，模型無法更動。

### 4.2 語音訊息輸入（繁體中文）

- 顧客可直接按住麥克風以**中文口語**詢問，無需打字。
- 系統下載語音檔、轉為 16kHz 單聲道 WAV、進行語音辨識，再進入同一套意圖／AI 流程。
- 回覆前會先回顯辨識結果（「我聽到的是：…」），讓顧客可自行確認是否聽錯，降低辨識錯誤造成的誤解。

### 4.3 AI 補充回覆

- 規則未命中時，由大型語言模型依「公司事實資料」生成回覆。
- 提示詞明確禁止：編造價格、承諾未提供之功能、虛構政府補助或優惠、揭露內部資料結構、自稱 AI 或語言模型。
- 無法回答時統一導向「這部分我需要請專人為您確認」，並保留顧客聯絡機會。

### 4.4 負責人即時通知

- 僅在**需要人工處理**的情況下發送通知（AI 無法回答之問題、預約請求），避免通知氾濫導致忽略。
- 通知管道：Telegram（店家指定帳號）。

### 4.5 對話紀錄與資料匯出

- 所有對話寫入結構化紀錄檔（JSONL）。
- 店家可透過專屬權杖（token）隨時匯出全部對話紀錄為 CSV（UTF-8 with BOM，可直接以 Excel 開啟）。
- 匯出端點預設關閉，未設定權杖時一律拒絕存取。

## 5. 技術規格

| 項目 | 規格 |
|---|---|
| 通訊通道 | LINE Messaging API v2（官方 HTTP API） |
| 服務介面 | HTTPS / TLS 1.2 以上（由 Cloudflare 終止） |
| 語言 | 繁體中文（台灣用語） |
| 輸入型態 | 文字訊息、語音訊息 |
| 輸出型態 | 文字訊息（單則上限 1,500 字元） |
| 語音辨識 | faster-whisper `small` 模型，int8 量化，CPU 推論，`language=zh`，beam size 5 |
| 音訊處理 | ffmpeg 轉檔為 16kHz 單聲道 WAV |
| AI 模型 | 透過 OpenRouter 呼叫 deepseek 系列語言模型（可替換） |
| 對話記憶 | 每位顧客保留最近 4 則訊息（2 輪對話） |
| 執行環境 | Linux，Python 3 虛擬環境，systemd 服務（自動重啟） |
| 資料存放 | 台灣境內主機（現行：新北市自有伺服器；規劃：遷移至台灣境內雲端區域） |

### 5.1 效能實測數據

以下為本系統於自有主機實測結果，非估算值：

| 情境 | 實測延遲 |
|---|---|
| 規則意圖回覆 | < 0.01 秒 |
| 語音辨識（模型已預載，暖機狀態） | 4–5 秒 |
| 語音辨識（首次冷啟動） | 7.3 秒 |
| 模型預載時間（服務啟動時） | 1.5–2.3 秒 |

**可用性**：服務以 systemd 常駐並設定自動重啟，全年無休運作。系統不因店家營業時間而停止；非營業時間之詢問仍會即時回覆。

## 6. 資訊安全設計

| 控制項 | 實作說明 |
|---|---|
| 訊息來源驗證 | 每一筆 webhook 請求均驗證 LINE 官方 `X-Line-Signature`（HMAC-SHA256），並以常數時間比較（`hmac.compare_digest`）避免時序攻擊 |
| 傳輸加密 | 全程 HTTPS／TLS，憑證由 Cloudflare 管理 |
| 網路暴露面 | **不對外開放任何 inbound 埠**；僅透過 Tunnel 建立 outbound 連線 |
| 請求大小限制 | 讀取前即檢查 `Content-Length`，上限 64 KB，防止以巨型請求耗盡資源 |
| 服務濫用防護 | 每位使用者每小時上限：AI 呼叫 20 次、通知 10 次；並限制追蹤使用者總數上限 |
| 憑證管理 | 存取權杖存於伺服器本機檔案，權限 600，不納入版本控制、不寫入程式碼 |
| 資料匯出保護 | 匯出端點需專屬權杖，未設定時預設停用；錯誤或不符一律回傳 403 |
| 服務隔離 | 以非特權（non-root）使用者帳號執行，服務單元已啟用 `NoNewPrivileges`、`PrivateTmp`、`ProtectSystem=strict`、`ProtectKernelTunables`、`ProtectControlGroups`、`RestrictSUIDSGID`；並以 `ReadWritePaths` 限定該服務僅能寫入自身服務目錄 |

> **誠實揭露**：現行主機磁碟未啟用全碟加密，亦尚未建立異地備份機制。上述兩項列為導入前改善項目（詳第 9 章），本文件不做超出事實之描述。

## 7. 個人資料保護與資料自主權

### 7.1 蒐集與處理

- 蒐集內容：LINE 使用者識別碼、訊息內容（文字或語音轉錄文字）、回覆內容。
- 語音原始檔於辨識完成後即刪除，**不保留音檔**，僅保留轉錄文字。
- 處理目的：回覆顧客詢問、店家營運分析。

### 7.2 保存期間

- 對話紀錄保存 **90 天**，逾期由系統**自動刪除**（每日檢查一次，服務啟動時亦執行一次）。
- 此為程式實際行為，非單純政策宣示。

### 7.3 委外處理揭露

- 規則意圖回覆：資料**不離開主機**。
- AI 補充回覆：未經腳本處理之問題內容會傳送至境外語言模型服務（OpenRouter，模型供應商 deepseek）。此為跨境傳輸，已於店家隱私政策中明確告知。
- 店家可選擇停用 AI 補充層，使所有回覆皆由本機規則處理。

### 7.4 資料自主權

- 店家為資料所有者。店家可隨時要求匯出全部對話紀錄（CSV 格式）。
- 店家終止服務時，可要求刪除全部資料；系統提供對應之清除作業。
- 顧客得依個人資料保護法行使查詢、閱覽、更正、刪除之權利。

### 7.5 誰能存取

- 僅店家指定之負責人。
- 服務提供者僅於維護或店家要求時存取，不作為其他用途。

## 8. 系統限制與不支援項目

以下為本方案**明確不提供**之功能，導入前應充分了解：

| 不支援項目 | 說明 |
|---|---|
| **金流與付款** | 不處理線上付款、信用卡、行動支付。本方案不經手任何金錢。 |
| **電子發票開立** | 不提供電子發票開立功能。店家須沿用原有開立方式。 |
| **POS／收銀系統** | 不提供、亦不取代 POS。如需整合，須另行串接店家既有系統。 |
| **點餐／外送平台整合** | 不串接 foodpanda、Uber Eats 等外送平台。 |
| **健保系統／病歷系統** | 不介接任何醫療資訊系統，不處理病歷或特種個資。 |
| **語音回覆（TTS）** | 僅支援語音**輸入**；回覆一律為文字。 |
| **圖片／檔案訊息** | 僅處理文字與語音，不處理圖片、貼圖、檔案。 |
| **自動排程寫入行事曆** | 預約為「登記 + 通知負責人」，非自動寫入店家行事曆。 |
| **多語系** | 目前僅支援繁體中文。 |

> **重要**：本系統定位為**顧客接待與詢問處理**工具，非營運系統（ERP／POS）。導入時不變更店家既有帳務、出單與發票流程，降低導入風險。

## 9. 部署與維運

### 9.1 導入流程（約 2 週）

| 階段 | 時程 | 工作內容 |
|---|---|---|
| 需求盤點 | 第 1–2 日 | 蒐集營業時間、價格、服務項目、常見問題、預約規則 |
| 系統建置 | 第 3–4 日 | 建立 LINE 頻道、部署服務、設定圖文選單、設定網域 |
| 驗收測試 | 第 5 日 | 20 題測試（含邊界情況），店家逐字確認對外措辭 |
| 人員訓練 | 第 6–7 日 | 30 分鐘教育訓練：AI 轉人工時如何處理、如何閱讀通知 |
| 上線觀察 | 第 2 週 | 監控首週詢問，調整關鍵字與事實資料 |

### 9.2 日常維運

- 服務自動重啟，無需人工介入。
- 每月檢視「AI 無法回答」之問題清單，回饋為事實資料更新。
- 資料保存 90 天自動清除，無需人工維護。

### 9.3 導入前待完成事項（誠實列示）

1. 建立每日備份機制
2. 評估啟用磁碟加密
3. 完成服務層級協議（SLA）文件並與實際架構一致
4. 遷移至台灣境內雲端區域，以取得可承諾之可用性

## 10. 與其他方案的差異

| 面向 | 外送平台 | 一般 POS／點餐系統 | 本方案 |
|---|---|---|---|
| 抽成 | 約 32–38% | 無 | 無抽成，月費制 |

| 主要價值 | 帶來新客流量 | 出單與帳務效率 | 接待詢問、降低人力負擔 |
| 是否經手金流 | 是 | 是 | **否** |

本方案可與上列系統並存，不取代既有 POS 或外送平台，僅補足「顧客詢問無人回應」之缺口。

## 11. 結語

本方案解決的是一個具體且可量化的問題：**店家在忙碌或非營業時間，無法即時回應顧客詢問，導致詢問流失。** 系統以最低的顧客端學習成本（沿用 LINE）、可控的對外措辭（規則優先）、與明確的資料自主權（可匯出、可刪除、90 天自動清除）達成此目標。

系統刻意不涉入金流、發票與 POS，以降低導入風險與法規複雜度，並確保與店家既有流程相容。
